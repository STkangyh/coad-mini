# 실시간(10 fps) incremental training — 가능한가, 병목은 무엇인가

Generated: 2026-07-27. 스크립트: [`dev/bench_realtime_incremental.py`](../dev/bench_realtime_incremental.py)
· 원시결과: `reports/realtime_incremental_raw.json`

**질문:** FeCAM을 baseline으로 놓고, **스마트글래스에서 카메라가 10 fps로 들어올 때
학습(incremental training)까지 실시간으로 도는가?** 안 되면 무엇이 막는가?

**세팅:** 데모의 스트리밍 경로(`app.py::frames_to_feature` → `fecam_predict`)를 그대로 모사.
프레임이 한 장씩 도착 → 16프레임 링버퍼 → **도착한 프레임만 인코딩**(batch=1, 스트리밍은
미래를 배칭할 수 없음) → mean-pool → (학습) → 예측. **CPU**, 48클래스 등록 상태.
예산 = **100 ms/frame**.

## 결론 — 통과, 그런데 병목이 예상과 다르다

| 모드 | 소요 | 유효 fps | 판정 |
|---|---|---|---|
| 예측만 | 24.73 ms | 40.4 fps | ✅ |
| **학습 + 예측 (incremental)** | **35.97 ms** | **27.8 fps** | ✅ **예산의 36%** |

10 fps는 **2.8배 여유**로 통과한다. 하지만 단계별로 뜯어보면 이상한 게 보인다.

## 단계별 실측 (CPU, 48클래스)

| 단계 | 평균 | p95 | 예산 대비 |
|---|---|---|---|
| 1. 전처리 (PIL→tensor) | 1.90 ms | 3.99 ms | 1.9% |
| **2. CLIP 인코딩 (batch=1)** | **22.78 ms** | 23.51 ms | **22.8%** |
| 3. 링버퍼 mean-pool | 0.00 ms | 0.00 ms | 0.0% |
| **4. FeCAM observe (학습)** | **0.25 ms** | 0.27 ms | **0.3%** |
| 5. FeCAM scores (캐시 warm) | 0.05 ms | 0.05 ms | 0.0% |
| 5b. FeCAM scores (캐시 cold) | 11.03 ms | 17.85 ms | 11.0% |
| 5c. └ 그중 **캐시 재계산** | **9.39 ms** | 13.99 ms | **9.4%** |

## ⭐ 병목 1 — 인코더 (63.3%), 예상대로

학습+예측 35.97 ms 중 **CLIP 인코딩이 22.78 ms(63.3%)**. `flops_result.md`에서
"인코더가 추론의 99.98%"라고 계산했던 것이 스트리밍 실측에서도 그대로 재현된다.

**주의할 차이:** 배치 처리 때 16프레임 묶음이 148 ms(프레임당 9.25 ms)였는데,
스트리밍은 **batch=1이라 프레임당 22.78 ms** — 약 2.5배 비싸다. 스트리밍은
배칭 이득을 못 받으므로 **배치 실험의 인코더 수치를 그대로 실시간에 대입하면 안 된다.**

## ⭐ 병목 2 — "학습 비용"의 97%가 실제로는 학습이 아니다 (개선 여지)

학습을 켰을 때 늘어난 비용은 **11.24 ms**인데, 그중 **진짜 학습(`observe`)은 0.25 ms뿐**이다.
나머지 **약 11 ms는 캐시 재계산**이다.

원인: `observe()`가 `self._cache = None`으로 precision 캐시를 무효화한다
(`fecam_head.py:80`). 그래서 **학습→예측을 매 프레임 번갈아 하면 D×D(512×512) 상관행렬
역행렬을 매번 다시 계산**한다. 배치 실험에서는 "한 번 fit → 여러 번 score"라 이 비용이
한 번만 발생해 **지금까지 한 번도 드러나지 않았던 항목**이다.

| | 비용 | 성격 |
|---|---|---|
| 실제 학습 (`observe`) | 0.25 ms | 필요 |
| 캐시 재계산 (D³ 역행렬) | 9.39 ms | **중복** — 매 프레임 반복 |

### 클래스 수와 무관한 고정 비용임을 확인

| 클래스 | observe | 캐시 재계산 | scores(warm) |
|---|---|---|---|
| 48 | 0.34 ms | 9.78 ms | 0.051 ms |
| 101 | 0.56 ms | 10.62 ms | 0.167 ms |
| 250 | 0.33 ms | 13.21 ms | 0.226 ms |
| 500 | 0.62 ms | 12.91 ms | 0.313 ms |

캐시 재계산은 **D³(D=512 고정)**이라 클래스가 500개로 늘어도 ~13 ms에서 멈춘다.
`scores`도 (이전 최적화 덕에) 500클래스에서 0.31 ms에 불과하다 →
**등록 클래스 수는 실시간성의 제약이 아니다.**

## 재계산을 미루면? — 정확도·속도 트레이드오프 실측

UCF101 실특징으로 온라인 스트리밍을 시뮬레이션(3,000샘플로 warm start → 800샘플을
한 장씩 예측 후 학습). 재계산 주기만 바꿔가며 측정:

| 재계산 주기 | 정확도 | ms/frame(헤드) | 헤드 유효 fps |
|---|---|---|---|
| **매 프레임 (현재)** | **98.38%** | 12.08 ms | 82.8 |
| 5회마다 | 97.62% | 2.62 ms | 381 |
| 20회마다 | 96.88% | 1.09 ms | 916 |
| 100회마다 | 96.88% | 0.67 ms | 1,498 |
| 아예 안 함 | 96.62% | 0.52 ms | 1,915 |

**5회마다로만 바꿔도 헤드가 4.6배 빨라지는 대신 정확도는 0.76%p 손해**다.
지금은 10 fps 예산에 여유가 있으므로 **정확도를 택하는 현재 설정이 옳다** —
다만 더 무거운 인코더를 쓰거나 더 느린 보드로 가면 **바로 꺼내 쓸 수 있는 카드**다.

## 종합 — 지금 상태와 남은 개선 여지

```
학습+예측 35.97 ms/frame  (27.8 fps, 10fps 예산의 36%)
├─ CLIP 인코딩   22.78 ms  63.3%   ← 진짜 병목, 인코더를 바꿔야 줄어듦
├─ 캐시 재계산    9.39 ms  26.1%   ← 중복 비용, 미루면 제거 가능
├─ 전처리         1.90 ms   5.3%
├─ 학습(observe)  0.25 ms   0.7%   ← 실제 학습은 사실상 공짜
└─ 예측(scores)   1.64 ms   4.6%
```

- **10 fps는 통과.** 30 fps(33 ms 예산)도 아슬아슬하게 가능(35.97 ms → 약간 초과).
- **실제 "학습"은 0.7%.** backprop-free head를 쓰는 이상, 증분 학습 자체는
  실시간성에 아무 위협이 아니다 — 이 프로젝트 주장의 직접 실측 근거.
- **개선 순위**: ① 인코더(63%) ② 캐시 재계산(26%). 헤드를 더 최적화해도 인코더가
  남으므로, 실시간 여유를 크게 늘리려면 결국 인코더를 건드려야 한다
  (`encoder_swap_result.md`의 결론과 일치).

## 후속 (미착수)

- **캐시 재계산 지연 옵션**을 `FeCAMHead`에 파라미터로 추가(`rebuild_every`) —
  위 트레이드오프 표가 근거. 지금은 예산 여유가 있어 보류.
- **30 fps 목표**로 올리면 캐시 재계산 제거가 필수가 된다(35.97 → 26.6 ms).
- 실제 임베디드 보드(Jetson/라즈베리파이)에서 같은 측정 — 맥북 CPU 기준이라
  절대 수치는 달라질 것. 갭 목록 1순위와 동일.
